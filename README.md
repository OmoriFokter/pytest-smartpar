# pytest-smartpar

Плагін pytest, що реалізує **метод паралельного виконання модульних тестів у
системах безперервної інтеграції** з урахуванням спільних файлів, спільного
стану процесу та тривалості тестів. Програмна частина статті «Метод
паралельного виконання модульних тестів у системах безперервної інтеграції»
(«АСУ та прилади автоматики», ХНУРЕ).

## Проблема і метод

`pytest-xdist` розподіляє тести між процесами-воркерами, але не враховує:

1. **спільні файли** – воркери є окремими процесами зі спільною файловою
   системою, тож тести, що одночасно пишуть і читають той самий файл,
   конфліктують;
2. **спільний стан у процесі** – глобальні змінні модулів, кеші,
   `os.environ`, поточний каталог: тест, що змінив стан і не відновив його,
   ламає інший тест на тому самому воркері (order-dependent тести);
3. **тривалість тестів** – «хвіст», коли один воркер ще працює, а інші вже
   простоюють.

Метод складається з п'яти кроків:

| Крок | Що робиться | Модуль |
|----|---|---|
| 1.&nbsp;Профілювання | множини файлів R/W кожного тесту (`sys.addaudithook`), зміни стану до/після тесту; пошук пар «забруднювач → жертва», крихких і NOD-тестів прогонами у випадковому порядку та delta debugging | `profiler.py`, `detector.py` |
| 2.&nbsp;Групування | тести, пов'язані конфліктом файлів (умови Бернштейна) або підтвердженою залежністю порядку, – одна група: один воркер, безпечний порядок | `graph.py` |
| 3.&nbsp;Планування | групи розподіляються між m воркерами за правилом LPT (Graham, 1969); рекомендоване m | `scheduler.py` |
| 4.&nbsp;Виконання | власний планувальник pytest-xdist виконує план; бар'єр для ізольованих тестів | `xdist_scheduling.py` |
| 5.&nbsp;Запис | історія тривалостей (EMA), run-файли, звіт | `history.py`, `report.py` |

Критерій одночасного виконання – умови Бернштейна (Bernstein, 1966):
`W(A)∩R(B)=∅`, `R(A)∩W(B)=∅`, `W(A)∩W(B)=∅`.

Межі застосування: модульні тести, Python ≥ 3.10, pytest ≥ 8, Linux як основна
платформа. Тести з базами даних, мережею, зовнішніми сервісами, E2E/UI не
охоплюються. Тести, нестабільні через час чи випадковість (NOD –
non-order-dependent), метод лише позначає й виконує окремо, але не «лікує».

## Встановлення й швидкий старт

```
git clone https://github.com/OmoriFokter/pytest-smartpar.git
cd pytest-smartpar
python -m pip install -e .            # pytest, pytest-xdist 3.3–3.8, pytest-randomly
python -m pip install -e ".[bench]"   # лише для експериментального стенду
```

Плагін підключається автоматично (entry point `pytest11`); без опцій
`--smartpar*` він нічого не робить.

Швидкий старт на контрольному проєкті (200 тестів із навмисно закладеними
залежностями, див. [нижче](#контрольний-проєкт)):

```
cd examples/control_project
pytest --smartpar-profile                       # 1. файли R/W, зміни стану
pytest --smartpar-detect --smartpar-seed 2026   # 1. order-dependent і NOD-тести
pytest -n 4 --smartpar                          # 4. перший запуск збирає тривалості
smartpar --dir .smartpar merge                  # 5. run-файли -> history.json
pytest -n 4 --smartpar                          # 2-4. групи, LPT, виконання
smartpar --dir .smartpar show                   # групи, хвіст, забруднювачі, T(m)
smartpar --dir .smartpar report                 # прогноз і фактичний час запусків
```

Два NOD-тести контрольного проєкту падають з імовірністю близько 20 % за
задумом, тому окремий запуск може завершитися з кодом 1.

## Режими, опції, вихідні файли

### Режими

| Команда | Що робить |
|---|---|
| `pytest --smartpar-profile [-n m]` | Профілювання: R/W файлів кожного тесту, зміни стану, які тест не відновив, порядок збирання. Без `-n` – послідовно (точніше); з `-n m` – кожен воркер профілює свою частину. Пише `dependencies.json`, лічильники в `history.json`. |
| `pytest --smartpar-detect` | Пошук order-dependent тестів дочірніми процесами pytest у випадковому порядку, кожен у власній копії проєкту. Пише `flaky.json`, доповнює `dependencies.json`. Потребує pytest-randomly. |
| `pytest -n m --smartpar` | Запуск за планом. `-n auto` – рекомендоване m (не більше доступних CPU). Пише `plan.json`, `results.xml`, `report.csv`, run-файл. |
| `smartpar merge [--alpha A]` | Зливає `runs/*.json` у `history.json` (EMA тривалостей, калібрування моделі накладних витрат). |
| `smartpar show [--max-workers N]` | Групи, ізольований хвіст, кандидати й підтверджені забруднювачі, крива `T(m)` і рекомендоване m. |
| `smartpar report [--last N]` | Останні запуски з `report.csv`: час, прогноз, похибка, падіння до/після перезапусків. |

Підкоманди `smartpar` приймають `--dir` (за замовчуванням `.smartpar`) перед
назвою підкоманди.

Режим запуску `--smartpar` записується в `report.csv` (`mode`):

| `mode` | Коли | Що відбувається |
|---|---|---|
| `smartpar` | є виміряні тривалості, сумісна версія xdist | власний планувальник xdist виконує план |
| `smartpar-bootstrap` | тривалостей ще немає | той самий планувальник, усі тести оцінено однаково (оцінка групи = кількість тестів); конфлікти файлів і підтверджені пари враховуються; прогін збирає тривалості |
| `smartpar-fallback` | `--smartpar-fallback` або версія xdist поза перевіреним діапазоном | `--dist loadgroup`: групи – `xdist_group`, порядок – за пріоритетом LPT; хвіст – окремим послідовним проходом |

### Опції pytest

| Опція | За замовч. | Призначення |
|---|---|---|
| `--smartpar` | – | запуск за планом (з `-n`) |
| `--smartpar-profile` | – | профілювання |
| `--smartpar-detect` | – | пошук order-dependent тестів |
| `--smartpar-runs N` | 20 | кількість прогонів у випадковому порядку |
| `--smartpar-seed S` | випадковий, записується | базовий seed детектора; прогони мають seed-и `S, S+1, …` |
| `--smartpar-detect-workers N` | доступні CPU | паралельні дочірні прогони детектора (підтвердження пар – не більше N/2) |
| `--smartpar-detect-budget SEC` | без обмеження | бюджет часу детектора; решта – `unresolved` |
| `--smartpar-strict` | вимк. | ненульовий код виходу, якщо новий тест упав, але пройшов при окремому перезапуску |
| `--smartpar-fallback` | вимк. | примусово `--dist loadgroup` (діагностика) |
| `--smartpar-dir PATH` | `.smartpar` | каталог даних |
| `--smartpar-alpha A` | 0.3 | коефіцієнт EMA тривалостей |

Опції ini (`pytest.ini`, `pyproject.toml`, …):

| Опція | За замовч. | Призначення |
|---|---|---|
| `smartpar_ignore_state` | `env:PYTEST_CURRENT_TEST`, `env:PYTEST_XDIST_WORKER`, `env:PYTEST_XDIST_WORKER_COUNT`, `env:COV_CORE_*` | fnmatch-шаблони ключів стану, які не порівнюються; значення з ini **замінює** список за замовчуванням |
| `smartpar_max_pair_checks` | 10 | прямі перевірки пар `[P, V]` перед delta debugging |
| `smartpar_max_orders_per_victim` | 3 | порядки, що аналізуються для однієї жертви (крихкого тесту) |

### Вихідні файли (`.smartpar/`)

Усі JSON мають `schema_version`, `generated_at`, `tool_version` і
записуються атомарно (тимчасовий файл + `os.replace`).

| Файл | Зміст |
|---|---|
| `history.json` | для кожного тесту `duration_ema` (лише за passed-прогонами; setup + call + teardown), `timed_runs`, `runs`, `last_outcome`, `fail_count`; модель накладних витрат `overhead` (`samples_s`, `counts`, `a`, `b`, `fit_points`, `model`); `last_merged_runs` |
| `dependencies.json` | `file_access` (R, W, `W_tree` – запис піддерева, `source` кожного доступу: `profile`/`detect`), `state_changes` (`модуль.атрибут`, `env:…`, `cwd`, `cache_growth:…`), `conflicts`, `order_edges`, `groups`, `collection_index`, `profile_stats` |
| `flaky.json` | `seeds`, `od_victims`, `od_brittle`, `nod`, `unresolved`, `detector` (base seed, seed-и прогонів у заданому порядку, межі пошуку, `truncated_victims`, режим ізоляції, тривалість) |
| `plan.json` | `workers`, `requested_workers`, `replanned`, `recommended_workers`, `predicted_makespan_s` і його складники, `predicted_curve`, `overhead_model`, `assignments`, `isolated_tail`, `tail_worker` |
| `results.xml` | JUnit XML; якщо `--junitxml` не задано – тут. Перезапуски й окремий прохід хвоста позначено властивостями `smartpar_rerun`, `smartpar_first_outcome`, `smartpar_suspected_dependency`, `smartpar_tail` |
| `report.csv` | рядок на воркер і `ALL`: `run_id, mode, workers, wall_time_s, predicted_wall_s, prediction_error_pct, sum_test_time_s, speedup_vs_history_serial, worker_id, worker_busy_s, worker_idle_s, worker_tests, failures, failures_before_rerun, failures_after_rerun, reruns, suspected_dependency, tail_mode` |
| `runs/run_<utc>_<pid>.json` | сирі дані запуску; звичайний запуск ніколи не редагує `history.json` |

## Відтворення експерименту

Експериментальний стенд – каталог `bench/`. Усі числа в статті беруться лише з
файлів серії, отриманих реальним прогоном; нічого не вписується вручну.

### 1. Підготовка машини

- Уся серія – **на одній машині**; порівнюються лише прогони однієї серії.
- Ноутбук – **від мережі живлення**, профіль енергоспоживання «продуктивність»
  (на Linux, наприклад, `cpupower frequency-set -g performance`); вимкнено
  режими енергозбереження й сну.
- **Закриті сторонні програми** (браузер, IDE, синхронізація хмарних дисків),
  вимкнено автоматичні оновлення та індексацію файлів на час серії.
- Код інструмента **закомічено**: якщо є незакомічені зміни в `src/`, `bench/`,
  `examples/` чи `pyproject.toml`, `run_benchmarks.py` виводить помітне
  попередження, а `env.json` містить `smartpar_dirty: true` і список файлів.
  Така серія не відтворюється за `smartpar_sha` і для статті не годиться.

### 2. Survey кандидатів

```
python -m pip install -e ".[bench]"
python bench/setup_projects.py --survey
```

Для кожного проєкту з `bench/projects.yaml`: клонування на зафіксованому SHA в
`bench/work/<проєкт>/src`, окремий venv у `bench/work/<проєкт>/venv`, один
послідовний прогін. Виводиться кількість тестів, час і кількість падінь «з
коробки»; результат – `bench/results/survey_<дата>.json`.

### 3. Вибір проєктів і фіксація SHA

У `bench/projects.yaml` для кожного вибраного проєкту:

- `sha` – повний SHA коміту (визначити: `git ls-remote <repo> refs/tags/<tag>`;
  для анотованого тегу – рядок `^{}`); `ref` – лише довідково;
- `install` – команди встановлення залежностей тестів;
- `deselect` – тести, що потребують мережі чи зовнішніх сервісів або падають
  «з коробки» (за результатами survey);
- `status: selected` замість `candidate`.

Зміни в `projects.yaml` комітяться до початку серії.

### 4. Прогін серії

```
python bench/setup_projects.py                 # якщо проєкти ще не встановлено
python bench/run_benchmarks.py --repeats 5 --workers 1 2 4 8
```

Для кожного проєкту:

- **Підготовка** (її час звітується окремо як накладні витрати методу):
  чистий стан → профілювання → детекція (seed фіксований, `--detect-seed`) →
  прогрівальні запуски smartpar для кожного m (`--warmup`, за замовчуванням 3:
  тривалості й калібрування моделі накладних витрат).
- **Вимірювання**: конфігурації `serial` (`-p no:xdist`), `xdist-load`,
  `xdist-loadfile`, `smartpar`; m ∈ `--workers`, але не більше фізичних ядер
  (m = 2 і 4 – розміри стандартних раннерів GitHub Actions; якщо їх немає,
  виводиться попередження); `--repeats` повторів; порядок прогонів
  перемішується в кожному повторі (seed `--order-seed` і кожен порядок
  записуються).
- **Чистий стан перед кожним прогоном**: `git checkout --force <SHA>` +
  `git clean -xdf` (залишки файлів попередніх прогонів впливають на результат);
  venv і дані smartpar лежать поза деревом проєкту; кожен вимір smartpar
  стартує зі свіжої копії підготовлених даних.
- Усі конфігурації – з `-p no:randomly` (звичайний порядок проєкту) і
  `-p bench.timing_plugin` (JSONL `nodeid, worker, start, end, outcome` – для
  діаграм Ганта однаково в усіх конфігураціях).

Результат – `bench/results/<дата>_<машина>/`: `env.json` (CPU, фізичні й
логічні ядра, RAM, ОС, версії Python/pytest/xdist/randomly/smartpar у venv
проєкту, `project_sha` кожного проєкту, `smartpar_sha`, `smartpar_dirty`, для
контрольного проєкту – `control_source`, дата, командний рядок) і `raw/`.

### 5. Аналіз

```
python bench/analyze.py bench/results/<дата>_<машина>
```

У `analysis/` серії:

- `times` – середнє, стандартне відхилення, 95 % довірчий інтервал
  (t-розподіл Стьюдента, вбудована таблиця для df = 1…30), прискорення
  `S(m) = T_serial / T(m)`, ефективність `E = S/m`, метрика Карпа–Флатта
  `e = (1/S − 1/m)/(1 − 1/m)`;
- `failures` – падіння до й після перезапусків для всіх конфігурацій (у
  базового xdist до = після); хибні падіння – тести, що впали в паралельній
  конфігурації й жодного разу не впали в послідовних прогонах серії (окрема
  колонка без NOD-тестів, знайдених детектором);
- `overhead` – час профілювання й детекції та **точка окупності**: скільки
  запусків CI потрібно, щоб виграш на запуск відносно найкращого базового
  xdist із тим самим m покрив ці накладні витрати;
- `prediction` – похибка прогнозу плану;
- `detection` – для контрольного проєкту precision/recall виявлення, з recall
  конфліктів файлів окремо для «profile» і «profile + detect»;
- рисунки (PNG 300 dpi і SVG, підписи українською, лінії розрізняються
  маркерами й штрихуванням, а не кольором): час при m = 4, діаграма Ганта
  воркерів (xdist-load проти smartpar), прискорення від m із кривою Амдала
  `S(m) = 1/(e + (1−e)/m)`, таблиця хибних падінь, precision/recall.

Таблиці – CSV і Markdown (для вставлення в статтю).

### 6. Публікація серії

Фінальна серія для статті копіюється в `bench/results/published/` і
комітиться (цей каталог, на відміну від решти `bench/results/`, не
ігнорується git):

```
cp -r bench/results/<дата>_<машина> bench/results/published/
git add bench/results/published/<дата>_<машина>
git commit -m "Publish benchmark series <дата>_<машина>"
```

Перед копіюванням варто перевірити в `env.json`, що `smartpar_dirty: false`.

### Контрольний проєкт

`examples/control_project` – пакет `ctrl` і 200 детермінованих тестів, у яких
навмисно закладено (і перелічено в `ground_truth.json`):

- 6 конфліктів файлів у `<project>/output` (по два W-R, R-W, W-W); два з них –
  умовні читання (`if exists(): read`, `hard_case: conditional_read`), яких
  один прогін профілювання у звичайному порядку не бачить;
- 5 пар «забруднювач → жертва»: глобальний dict модуля, `lru_cache`,
  `os.environ`, `os.chdir`, атрибут класу-синглтона;
- 3 крихкі тести (потребують стану, який готує інший тест);
- 2 NOD-тести (падають з імовірністю близько 20 % через `random.SystemRandom`,
  який pytest-randomly не перезадає);
- 10 довгих тестів (0.3–1.5 с), решта – мілісекунди;
- 4 тести, що змінюють стан, але відновлюють його через `monkeypatch` (метод не
  має їх позначати).

У звичайному послідовному порядку всі тести, крім NOD, проходять. Тест
інструмента `pytest -m control` (за замовчуванням вимкнений через тривалість)
перевіряє на копії проєкту: лише після профілювання precision = 1, а
пропущено можуть бути тільки умовні читання; після profile + detect конфлікти
файлів, пари «забруднювач → жертва» і крихкі тести збігаються з
`ground_truth.json` точно (precision = recall = 1); NOD-тест ніколи не
потрапляє в залежності порядку; у 10 повторах `-n 4 --smartpar` немає падінь,
крім NOD.

## Дизайн-рішення

### Профілювання

- **Файли** – через `sys.addaudithook`: події `open`, `os.remove`,
  `os.rename`, `os.mkdir`, `os.rmdir`, `shutil.rmtree`, `shutil.copyfile`,
  `shutil.move` (сигнатури перевірено на Python 3.12 і 3.14: `os.unlink` подає
  подію `os.remove`, `os.replace` – `os.rename`, відсутній `dir_fd` = −1).
  Запис – mode з `w a x +` або прапорці `O_WRONLY|O_RDWR|O_APPEND|O_CREAT|O_TRUNC`.
  `rmtree`, `rmdir`, перейменування/переміщення каталогу – запис **усього
  піддерева** (`W_tree`, збіг за префіксом). `mkdir`/`makedirs` наявного
  каталогу – не запис; створення нового каталогу – запис лише цього шляху.
  Хук ставиться один раз на процес і ніколи не кидає винятків.
- **Стан** – знімки до/після тесту: атрибути модулів проєкту (поза каталогами
  тестів) і атрибути даних їхніх класів (стан синглтонів), `os.environ`, cwd,
  `sys.path`, кореневий логер. Відбиток – хеш `pickle`; для несеріалізовних
  об'єктів з `__dict__` – неглибокий відбиток `vars(obj)`. Тест, що відновив
  стан (`monkeypatch`), різниці не має. Модуль, імпортований під час тесту,
  сам не є зміною, але побічні ефекти імпорту – є. Ріст кешу `lru_cache` –
  окрема слабка категорія `cache_growth:`.
- **Прогони профілювання** оновлюють у `history.json` лише лічильники, а не
  тривалості: інструментування спотворює час.

### Пошук order-dependent тестів

- `runs` прогонів у випадковому порядку (seed-и `S, S+1, …`); кожен тест, що
  хоч раз упав, – окремо k = 3 рази: падає іноді – **NOD**; падає завжди, але в
  якомусь порядку пройшов – кандидат у **крихкі**; окремо завжди проходить –
  кандидат у **жертви**.
- Пошук забруднювача (setter-а для крихкого): спершу пари `[P, V]` для тестів
  зі змінами стану (`cache_growth` – останніми), потім delta debugging (ddmin).
  Кожна пара **підтверджується свіжими процесами** (`[P, V]` падає й `[V]`
  проходить, по 2 рази); у `flaky.json` – лише підтверджені. Кандидат у жертви
  без підтвердженого забруднювача ще 5 разів запускається окремо: впав – NOD,
  ні – `unresolved`.
- **Ізоляція**: кожен дочірній прогін – свіжий процес у власній копії проєкту
  (без `.git`, `.smartpar`, venv і кешів), з `PYTHONPATH` на копію. Без цього
  паралельні прогони в одній папці через спільні файли дали б хибні
  залежності. Якщо копіювання неможливе – послідовно в папці проєкту.
- Прогони в заданому порядку теж ідуть з pytest-randomly, але без
  перемішування й кожен зі своїм seed-ом: pytest-randomly перезадає seed
  `random` перед кожним тестом, і з однаковим seed-ом ізольовані прогони
  NOD-тесту були б однаковими. Відтворюваність повна.
- У кожному дочірньому прогоні ввімкнено аудит-хук (без знімків стану);
  знайдені доступи до файлів об'єднуються з профілюванням із позначкою джерела
  `detect`.
- **Ймовірність виявлення NOD**: якщо тест падає незалежно з ймовірністю `p`,
  імовірність хоча б одного падіння за `n` прогонів дорівнює `1 − (1 − p)^n`.
  Для ізольованих прогонів `n = k` (3, з додатковими – до 8): для `p = 0.2`
  `k = 3` → 0.488, `k = 8` → 0.832; щоб тест узагалі потрапив до розгляду, він
  має впасти у випадкових прогонах: `runs = 20` → 0.988.

### Граф і планування

- Ребра графа – **лише** конфлікти файлів (умови Бернштейна, інвертований
  індекс ресурсів) і **підтверджені** пари з `flaky.json`. Зміни стану самі по
  собі ребер не створюють: це лише кандидати для детектора.
- Пов'язані тести – одна група (union-find): один воркер, топологічний порядок
  за ребрами порядку, нічиї – за порядком збирання тестів (тривалість усередині
  воркера не впливає на makespan).
- **Ізольований хвіст**: NOD-тести, тести на циклі ребер порядку і все, що за
  ребрами має йти після них. Виконується після **бар'єра**: воркер xdist
  утримує останній отриманий тест до приходу наступного або `shutdown`, тому
  воркери без хвоста одразу отримують `shutdown` після свого списку, а воркер
  хвоста отримує хвіст, коли в нього лишився тільки утримуваний тест і всі інші
  воркери завершились.
- **LPT** (Graham, 1969): групи за спаданням тривалості – на найменш
  завантажений воркер; нічиї – за nodeid і номером воркера (план
  детермінований). Тест без виміряної тривалості – медіана відомих.
- **Нові тести** (немає в історії) плануються звичайно; новий тест, що впав,
  перезапускається окремим дочірнім процесом після сесії: упав знову –
  звичайне падіння, пройшов – passed з позначкою `suspected_dependency`.
  Перезапуски видно в терміналі, run-файлі, `report.csv` і `results.xml`;
  падіння рахуються до й після перезапусків.
- **Рекомендоване m**: `T(m) = LPT(m) + хвіст + a + b·m`, обирається найменше m
  з `T(m) ≤ 1.05·min T`. `a`, `b` – найменші квадрати за виміряними накладними
  витратами при m = 1, 2, 4; точка використовується лише після 3 чистих
  прогонів, до того – модель за замовчуванням `a = b = 0`
  (`overhead_model` у `plan.json`). Модель – гіпотеза, її точність оцінює
  експеримент.
- **Історія** – модель «читачі–письменники» без блокувань: запуск лише читає
  `history.json` і пише окремий run-файл; `smartpar merge` зливає їх (EMA
  тривалостей лише за passed-прогонами) і переносить у `runs/merged/`; злиття
  двофазне й відновлюється після збою без подвійного врахування.

### Сумісність з pytest-xdist

Власний планувальник реалізує **внутрішній** інтерфейс планувальника xdist
(той самий, що `LoadScheduling`) і покладається на поведінку воркера
(утримання останнього тесту, виконання в порядку отримання). Це не публічний
API, тож дозволено лише версії, на яких проходить увесь набір тестів:
`pytest-xdist>=3.3,<3.9` (перевірено 3.3.1, 3.4.0, 3.5.0, 3.6.1, 3.7.0, 3.8.0;
CI-задача `xdist-compat`). Поза діапазоном smartpar автоматично переходить у
fallback (`--dist loadgroup`) і повідомляє про це.

## Обмеження

- **Динамічне профілювання бачить лише доступи, що сталися.** Якщо тест
  звертається до файлу умовно (наприклад, читає лише якщо файл існує), а файлу
  під час профілювання немає, читання не записується, і конфлікт не
  знаходиться. Так само зміна стану, що залежить від порядку, у послідовному
  профілюванні може не проявитися. Прогони детектора у випадкових порядках
  частково компенсують це (їхні доступи записуються з джерелом `detect`), але
  гарантії немає: доступ, що не стався в жодному прогоні, лишається невидимим.
- **Стан робочої копії.** Копії проєкту для детектора містять файли, що
  залишилися в папці проєкту (наприклад, після профілювання), тож результат
  залежить від її стану. Бенчмарк тому завжди починає з `git clean -xdf`.
- **Файли.** Видно лише операції Python-рівня: C-розширення, що звертаються
  до файлів напряму, аудит-хук обходять. Подія `open` не містить `dir_fd`, тож
  `os.open(відносний_шлях, dir_fd=fd)` розв'язується відносно cwd; інші
  відносні шляхи з `dir_fd` пропускаються (`profile_stats.unresolved_dir_fd`).
  Символьні посилання не розкриваються. Ігноруються `tmp_path`, стандартна
  бібліотека, `site-packages`, `/dev`, `/proc`, `/sys`, `*.py`/`*.pyc`.
  Перевірка `isdir` в аудит-хуку бачить стан до операції; гонки між
  перевіркою й операцією можливі лише при паралельному профілюванні.
- **Стан.** Значення без `pickle` і `__dict__` порівнюється за `repr` (4 КБ),
  а якщо й це неможливо – за ідентичністю об'єкта. Модуль, знімок якого
  триває понад 50 мс, переходить у дешевий режим (видно лише перепризначення
  атрибута). Будь-який виклик `lru_cache` з новим аргументом – слабкий
  кандидат. Фікстури рівня сесії/модуля приписуються тесту, під час якого їх
  створено або знищено.
- **Детектор.** NOD із малою ймовірністю падіння може лишитися непоміченим
  (формула вище). Код, імпортований не з папки проєкту, спільний для всіх
  копій. Тести, чутливі до абсолютного шляху проєкту, у копії можуть
  поводитися інакше. Комбінацію кількох забруднювачів ddmin знаходить, але за
  більшу кількість прогонів.
- **Історія.** EMA залежить від порядку прогонів; детермінізм гарантовано для
  фіксованого набору прогонів в одному злитті (порядок `(started_at, run_id)`).
  Запізнілий прогін не губиться, але застосовується останнім.
- **Fallback-режим**: підсумок pytest «N passed» рахує лише основну сесію;
  результати окремого проходу хвоста – у секції `smartpar`, run-файлі,
  `report.csv` і `results.xml`.
- `report.csv` дописується одним `write` з `O_APPEND`: атомарність гарантована
  лише на локальній файловій системі; основне джерело даних – run-файли.
  Захист від одночасних `smartpar merge` (`flock`) – лише на POSIX.

## English summary

**pytest-smartpar** is a pytest plugin implementing the method from the article
*A Method for Parallel Execution of Unit Tests in Continuous Integration
Systems*. It profiles every test (files read and written via
`sys.addaudithook`, process state changes via before/after snapshots), detects
order-dependent tests with random-order runs, delta debugging and confirmation
in fresh processes (each run in its own copy of the project), groups tests
connected by file conflicts (Bernstein's conditions) or confirmed order
dependencies, schedules the groups on m workers with LPT through a custom
pytest-xdist scheduler (with a barrier for isolated tests), and records run
history. `bench/` contains the reproducible experimental stand (clean state per
run, shuffled configuration order, separate accounting of profiling/detection
overhead, break-even analysis); `examples/control_project` is a test suite with
planted dependencies and a ground truth. License: MIT.
